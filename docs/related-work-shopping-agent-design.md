# 购物类浏览器智能体设计说明

这次调整不是把提示词写长，而是把购物推荐建模成可观察、可回退、可验证的 Web Agent 工作流。现在这些购物阶段不是必须按固定顺序执行的脚本；启用 LLM 时，它们作为 evidence checklist 交给动态 agent loop，由 agent 根据当前页面状态决定下一步动作。

## 相关工作依据

- [WebShop](https://arxiv.org/abs/2207.01206) 把购物任务定义为真实商品约束下的交互式网页任务，强调组合需求理解、查询重写、商品页噪声文本理解和策略性探索。对应到本项目，购物推荐不能只搜索“耳机推荐”，而要分阶段形成候选池、进入商品页、阅读评论和比较缺点。
- [WebArena](https://arxiv.org/abs/2307.13854) 强调真实网站上的长程任务、页面状态观察和功能正确性验证。对应到本项目，浏览器标题变化不等于任务完成，必须记录每一步页面证据，并判断是否满足目标。
- [Mind2Web](https://arxiv.org/abs/2306.06070) 关注跨真实网站的多步骤任务分解。对应到本项目，agent 应把“推荐耳机”拆成搜索、候选抽取、商品页核对、评论观察、视频测评观察和最终比较。
- [ReAct](https://arxiv.org/abs/2210.03629) 将推理和行动交替执行，用观察结果更新后续行动。对应到本项目，LLM 可以增强计划，但执行层仍要保留明确动作节点和证据阶段，避免只输出一段不可验证的思考。

## 设计原则

- 规划不是 prompt-only：LLM 返回的 search plan 会被规范化为证据阶段；如果 DeepSeek 只返回泛化查询，系统会自动补齐缺失阶段。
- 行动链必须外显：每个搜索/抽取节点带 `evidence_stage`，前端和报告都能显示当前是在找候选池、商城页、专业测评、用户差评还是视频测评。
- 页面状态要闭环：商品页深读在视频页打开之前执行，避免浏览器上下文切到视频站后丢失商品候选。
- 报告要区分证据来源：最终 Markdown 会展示 search plan、source readings、comparison matrix、video digest 和 uncertainties。

## 当前购物场景节点

1. 打开搜索入口。
2. 搜索榜单/专业评测，建立预算内候选池。
3. 抽取候选品牌、型号和初步链接。
4. 搜索商城/商品页线索，核对价格、参数、销量和评价入口。
5. 抽取商城商品页和评论入口。
6. 搜索具体型号横向对比和缺点测评。
7. 抽取专业测评和对比链接。
8. 搜索用户评论和差评。
9. 抽取长期使用体验、佩戴、底噪、夹头和连接稳定性证据。
10. 深读 Top 商品/评测/商城候选，存储价格、参数、评价和风险点。
11. 搜索测评视频和视频评论。
12. 抽取视频候选和评论区线索。
13. 打开最相关测评视频页面。
14. 读取视频元数据、简介、可见评论/字幕和关键帧预留信息。
15. 综合商品页、用户评论、专业评测和视频证据生成购买建议。

## 与提示词方案的区别

提示词只能要求模型“多想一点”；这个实现把“多想一点”拆成了稳定的执行结构：

- `default_search_plan("shopping")` 固化五个证据阶段。
- `plan_next_action()` 每轮读取当前页面、候选链接、memory 和 checklist，再选择下一步安全动作。
- 旧的固定购物动作模板已删除；`default_search_plan("shopping")` 只作为 checklist，不直接决定执行顺序。
- 测试用例断言购物 workflow、默认 plan 和稀疏 LLM plan 都包含五个阶段。
